# student-care

> 위치: `docs/specs/wangyu/features/student-care.md`  
> Entity / State 정의는 `docs/specs/wangyu/domain.md`, API 형식은 `docs/api/api-contract.md` §65을 따른다.

## 1. Scope

관리자(원장 / 매니저)가 지점 학생 중 **평소와 달라진 학생**을 찾아 사유를 확인하고, 필요하면 학생과 약속 한 가지를 정한 뒤
**같은 기준으로 다시 확인**한다. 과정은 학생 기록에 남아 담당이 바뀌어도 이어받는다.

```text
신호(달라진 학생) → 사유 확인 → 약속 → 다시 확인 → 선생님 결정
```

포함:

```text
케어 보드: 확인할 변화 / 조정 진행 중 / 판단 보류
학생 상세: 근거, 최근 14일 학습량 그래프(평소 하루 평균선), 확인할 질문
사유 확인: 예상된 변화 / 기록 문제 / 조정 필요
약속: 목표 한 가지 · 행동 · 부담 한도 · 재점검일 · 학생과 합의 (예시로 채워짐)
재점검: 같은 기준으로 다시 비교, 결과 표시(판정이 아닌 비교)
선생님 결정: 종결 / 같은 약속으로 계속 / 약속 수정
면담·통화 메모
학생 기록 (Timeline)
기준값 (신호 Threshold) 조회 / 수정
지점 요약
```

제외:

```text
성적 신호(등급 하락, 교재 정답률 하락)
성적·시험 현황에서 케어 시작
기존 학습계획 자동 변경 (시안의 "계획 변경안")
학부모 발송 / 문자
```

## 2. Surface / 경로

```text
Admin 콘솔 › 학습관리 › [지점]학생 케어
frontend/admin  →  /api/admin/student-care/**
```

화면 구성:

| 영역 | 내용 |
|---|---|
| 왼쪽 | 지점 목록(검색). 지점을 고르면 그 지점 기준으로 다시 불러온다. |
| 상단 탭 | 케어 보드 · 학생 기록 · 기준값 · 지점 요약 |
| 케어 보드 헤더 | `<기준일> 기준 · <지점명>`, 판단 보류 학생 한 줄 안내 |

## 3. 케어 보드

### 3-1. 확인할 변화

- 신호가 하나 이상 있고, 진행 중인 케어 건이 없는 학생.
- 카드: 학생 이름, 신호 배지(여러 개 가능), 첫 신호의 요약 한 줄.
- 개수 표시.
- 정렬: 신호 수 많은 순 → 이름 순.
- 최근 종결된 케어 건이 있으면 `cooldownDays` 동안 같은 신호로 다시 올리지 않는다.

### 3-2. 조정 진행 중

- 상태가 `IN_ADJUSTMENT`인 케어 건.
- 카드: 학생 이름, 약속 목표, 재점검일, 재점검일이 되었으면 "재점검" 표시.
- 정렬: 재점검이 된 건 먼저 → 재점검일 빠른 순.

### 3-3. 판단 보류

- 최근 7일 유효 학습일(30분 이상)이 `minValidDays` 미만이라 학습량 계열 신호를 비교하지 않은 학생.
- 출결 신호(연속 미입실)가 있으면 판단 보류가 아니라 확인할 변화에 들어간다.
- 문구: `<이름> 최근 7일 유효 학습일 N일 · 기록이 적어 학습량을 비교하지 않습니다`.

### 3-4. 빈 상태 / 에러

- 확인할 변화 0건: "평소와 달라진 학생이 없습니다".
- 기존 학습 데이터 연동 실패: 에러 안내 + 다시 시도. 빈 목록으로 보여 주지 않는다.

## 4. 학생 상세 (카드 선택)

```text
<이름> <신호 라벨들>
근거        · 신호별 근거 문장
그래프      최근 14일 하루 학습량(분), 평소 하루 평균 점선, 최근 7일 구분
확인할 질문 신호별 질문 (판정하지 않음)
사유 확인   예상된 변화 | 기록 문제 | 조정 필요
```

### 4-1. 예상된 변화 / 기록 문제

- 선택 후 메모(선택)를 남기고 "기록하고 종결"을 누르면 케어 건이 바로 종결된다.
- 예상된 변화: 시험 뒤 휴식, 시간표 변경 등. 기록만 남기고 종결.
- 기록 문제: 타이머 누락, 기기 문제. 기록 확인으로 넘김.

### 4-2. 조정 필요

입력 (예시로 채워짐, 수정 가능):

| 항목 | 필수 | 규칙 |
|---|---|---|
| 목표 한 가지 | O | 1~200자 |
| 행동 | O | 1~200자 |
| 부담 한도 | X | 0~100자 |
| 재점검일 | O | 기준일 다음 날 ~ 28일 뒤. 선택지: 3일 / 7일 / 14일 뒤 |
| 학생과 합의함 | O | 체크해야 "조정 시작" 가능 |

"조정 시작" → 상태 `IN_ADJUSTMENT`, 확인할 변화에서 조정 진행 중으로 이동.
중복 클릭 / 이미 진행 중인 건이 있으면 새 건을 만들지 않는다.

### 4-3. 조정 진행 중 상세

- 이 건의 기록(Timeline), 조정 약속 요약(목표 · 행동 · 부담 한도 · 합의).
- 재점검일 전: "재점검일(M월 D일)에 같은 기준으로 다시 비교합니다".
- 면담·통화 메모 추가: 구분(면담 / 통화 / 메시지 / 기타) + 내용(1~1000자).

### 4-4. 재점검

재점검일이 되면(기준일 ≥ 재점검일):

```text
재점검 · 같은 기준으로 다시 비교
<신호 라벨> <처음 값> → <지금 값> (기준 / 목표)
결과 표시 <변화 관찰 | 변화 없음 | 더 나빠짐 | 일부 변화> · 판정이 아니라 비교 결과입니다
선생님 결정  [종결] [같은 약속으로 계속] [약속 수정]
```

- 종결: 상태 `CLOSED`.
- 같은 약속으로 계속: 새 재점검일 선택 → `IN_ADJUSTMENT` 유지.
- 약속 수정: 약속 입력 폼이 다시 열림 → 저장 시 새 약속 / 새 재점검일.
- 재점검일 전에는 결정 버튼이 없다(서버도 거부).

## 5. 학생 기록 탭

- 케어 보드에서 고른 학생의 모든 케어 건 이벤트를 최신순 Timeline으로 보여 준다.
- 표시: 날짜, 종류(사유 확인 / 조정 / 재점검 / 결과·종결 / 메모), 내용.
- 학생을 고르지 않았으면 "케어 보드에서 카드를 고르면 그 학생의 기록이 보입니다".

## 6. 기준값 탭

| 키 | 기본값 | 의미 |
|---|---|---|
| `absenceDays` | 3 | 연속 미입실 일수 이상 |
| `planMissingDays` | 3 | 최근 7일 중 계획 미제출 일수 이상 |
| `studyDropPercent` | 40 | 최근 7일 학습량이 평소 대비 N% 이상 감소 |
| `executionRatePercent` | 60 | 최근 14일 계획 대비 실행률 N% 미만 |
| `subjectShareGapPoints` | 15 | 계획 과목 비중과 실제 비중 차이 N%p 이상 |
| `startShiftMinutes` | 90 | 평소 대비 시작 시각이 N분 이상 늦어짐 |
| `minValidDays` | 3 | 최근 7일 유효 학습일이 N일 미만이면 판단 보류 |
| `cooldownDays` | 7 | 종결 후 같은 신호를 다시 올리지 않는 기간 |

수정은 지점 단위. 범위 밖 값은 422.

## 7. 지점 요약 탭

- 확인할 변화 수, 판단 보류 수, 조정 진행 중 수, 재점검 도래 수.
- 신호별 학생 수.
- 최근 30일 종결: 예상된 변화 / 기록 문제 / 재점검 후 종결.

## 8. Guardrail

- 신호와 비교 결과는 **판정이 아니다**. 사유 선택과 종결은 선생님이 한다.
- 예시 문구(약속 예시, 확인할 질문)는 규칙 기반 템플릿이며 AI 결과가 아니다.
- 학생 케어는 Existing 출결·학습·계획을 읽기만 한다.
- Mentor Surface에 이 데이터를 노출하지 않는다.

## 9. 완료 기준

- [ ] 신호 6종 + 판단 보류가 기준값대로 계산된다 (Unit Test).
- [ ] 사유 확인 3종, 조정 시작, 재점검, 결정 3종이 상태 전이 규칙대로 동작하고 잘못된 전이는 409 (Unit / Integration Test).
- [ ] 학생 기록 Timeline에 모든 이벤트가 남는다.
- [ ] 기준값 수정이 보드에 반영된다.
- [ ] Admin 화면에서 신호 → 사유 → 약속 → 재점검 → 종결 E2E가 통과한다.
