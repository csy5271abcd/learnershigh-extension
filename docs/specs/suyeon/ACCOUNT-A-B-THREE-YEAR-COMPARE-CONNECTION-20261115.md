# 계정 A ↔ 계정 B: 학년도별 평가계획서 비교 연결 계약 검토 (A8, 2026-11-15 · 제안)

> 결론: **A7 공식 비교(관리자 확정값, `CONFIRMED_ONLY`)는 그대로 유지**하고, 계정 B `three-year-compare-0.1`은 **관리자 검토용 후보**로만 붙인다. 계정 A Backend 안에서 Python을 실행하지 않는다. 연결 방식(실행 위치·API)은 아래 결정 후 구현한다. 계정 B 코드는 읽기만 했다.

## 1. 두 구현의 차이

| 항목 | 계정 A (§38-5, 구현됨) | 계정 B `tools/compare3y/three_year.py` (CLI·모듈) |
|---|---|---|
| 입력 | 학년도별 **최신 확정 Revision의 관리자 확정값** | 학년도별 **분석 결과**(서비스 응답·Adapter·payload, 0.2·0.3 혼합 가능) |
| 의미 | 공식 비교(사람이 확정한 값만) | 기계 매칭·변경 **후보**. `confirmed[]` = 규칙상 유일 일치일 뿐, `humanConfirmed: false` |
| 과목 동일성 | 학년도마다 관리자가 고른 학업 과목 ID | 분석 결과 과목 키(이름 정규화 등) — 비슷한 이름·다른 과목은 REMOVED/ADDED 후보(C11) |
| 항목 매칭 | 확정 이름이 같을 때만(공백 정리). 1:1로 빠지고 생기면 `POSSIBLE_RENAME` | 이름 + 내용·채점표·속성 근거, 1:1, `AMBIGUOUS_MATCH`, 같은 이름·다른 내용 `REVIEW_REQUIRED`(C06), 방법 변경 `methodChanged`(C16) |
| 비교 필드 | 확정 대상 필드만(반영비율·만점·시기·이름), 채점기준은 항상 비교 불가 | 채점표 세부(C13), 운영계획(C14), Locator 보존(C15) |
| 부분 추출 | 확정 안 된 값은 `NOT_CONFIRMED`/`NOT_AVAILABLE` | 추출 불완전한 해가 끼면 `NOT_COMPARABLE`(삭제·추가로 세지 않음, C09) |

중복 부분(필드 수치 비교·누락 학년도·비슷한 이름의 다른 과목 구분)은 A7 구현을 유지한다.

## 2. 계정 A 공식 비교의 알려진 한계 (B 엔진이 보완할 수 있는 곳)

1. **같은 이름·다른 내용(C06)**: 계정 A는 평가 내용이 확정 필드가 아니어서 이름·반영비율·만점·시기가 같으면 `SAME`으로 본다. 화면 문구 "확정값 기준"으로 한계를 알리지만, B의 `SAME_NAME_DIFFERENT_CONTENT` 후보를 함께 보이면 관리자가 놓치지 않는다.
2. **채점표·운영계획 변화(C13·C14)**: 계정 A는 비교하지 않는다(채점기준 = 비교 불가, 운영계획 = 행 수만).
3. **명칭 변경 근거(C05)**: 계정 A는 1:1 빠짐·생김만으로 표시. B는 내용 근거 점수를 준다.

## 3. 연결 제안 (결정 대기)

```
관리자 비교 화면 (§38-5 공식 표)  ─┬─ 그대로
                                     └─ [분석 후보 비교 · 관리자 미검증] 별도 영역
                                          ↑ 계정 B 비교 결과 (three-year-compare-0.1, humanConfirmed=false)
```

- **입력 선택**: 학년도마다 공식 비교가 쓴 그 확정 Revision의 **확정에 쓰인 분석 결과**(`assessment_plan_review.analysis_id` → Run `result_json`)를 넘긴다. 원문 Locator는 그 Run에 그대로 있다.
- **실행 위치 (택1, 계정 B 결정)**: (a) 분석 서비스에 `POST /compare-three-year`(학년도별 payload 묶음 → 비교 JSON) 추가 — 계정 A는 HTTP Client만 / (b) 계정 B 배치가 결과 파일을 만들고 계정 A가 가져오기(수동). **계정 A Backend에서 Python 실행(프로세스 호출)은 하지 않는다.**
- **저장**: 새 테이블(예: `assessment_plan_comparison_candidate` — 입력 Run ID 목록·스키마 버전·결과 JSON·생성 시각). 공식 확정값과 섞지 않고, 학생에게 보내지 않는다.
- **표시**: `confirmed[]`도 "규칙상 일치(사람 미확인)"로 표시. 공식 표의 상태를 B 결과로 바꾸지 않는다.

## 4. 결정 요청

1. 실행 위치 (a)/(b)와 HTTP 요청·응답 모양(학년도·Run ID·payload 전달 방식, 크기 상한).
2. B `comparisonKey`(`S:<과목키>|…|<연도>:<itemKey>`)와 계정 A 확정값(과목 ID·`performanceEvaluation.items[n]`)을 잇는 방법 — 관리자가 고른 과목 ID를 B 입력에 함께 넘길지.
3. 0.2·0.3 혼합 학년도의 운영계획 비교 표시(C12 — B는 `NOT_COMPARABLE`).
4. 후보 비교를 언제 계산할지(비교 화면 열 때 / 확정 시점 / 수동 버튼).

## 5. 검증 상태

- 계정 A 공식 비교: Integration 5 · E2E 1(합성, Stub 분석 결과). **실제 학교 3개년 문서 비교는 하지 않았다**(같은 학교 3개 학년도 확정 자료가 없음).
- 계정 B 엔진: 계정 B 보고 기준 Fixture 17종·테스트 20건 통과(계정 A는 실행하지 않았고, Fixture 목록·판정 규칙만 확인).
