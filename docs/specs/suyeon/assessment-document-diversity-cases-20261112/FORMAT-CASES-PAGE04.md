## A-2. 형식별 대표 문서 심층 [원본 확인]

같은 학교(대신고)의 HWP와 HWPX 내부를 비교했다:

| 항목 | 대신고 2024 HWP (F03312) | 대신고 2025 HWPX (F03502) |
|---|---|---|
| 첫 바이트 | `D0 CF 11 E0 A1 B1 1A E1` (OLE 복합 문서) | `50 4B 03 04` (ZIP) |
| 내부 구성 | 스트림: `FileHeader`, `DocInfo`, `BodyText/Section0`(압축 이진 레코드), `BinData`, `PrvText`, `Scripts` 등 | 파일: `mimetype`(`application/hwp+zip`), `Contents/header.xml`, `Contents/section0.xml`, `BinData/*.jpg`, `META-INF/*` |
| 본문 읽는 법 | OLE 섹터 표 → 스트림 → raw deflate 해제 → HWP 레코드(문단·표·셀 컨트롤) 해석 | ZIP 해제 → XML 요소(`hp:tbl`, `hp:tc`, `cellSpan`) 해석 |
| 이번 결과 | 문단 472 · 표 11 · 셀 313 · 병합 29 | 문단 433 · 표 12 · 셀 290 · 병합 25 |

같은 학교·같은 양식이어도 바이트 구조가 완전히 다르다. 그래서 HWP·HWPX·PDF 각각 Parser를 따로 두고, 결과를 하나의 DocumentModel(문단·표·셀·병합·Locator)로 맞춘다.

## A-3. 형식 차이가 Parser 구현에 미친 영향

| 형식 | 이번 표본에서 본 문제 | 그래서 만든 처리 |
|---|---|---|
| HWP | 이진 레코드, 압축, 표·셀이 문단 안 컨트롤로 들어 있음 | OLE·레코드 Parser를 외부 라이브러리 없이 구현(`hwp5.py`, `hwp_model.py`) |
| HWPX | ZIP + XML, 확장자 위장 | 첫 바이트로 판정, XML의 셀 병합 속성을 그대로 격자로(`hwpx_model.py`) |
| PDF | 표 구조가 없음(글자 좌표와 선만 있음), 가로·세로 쪽 섞임, 쪽 경계에서 표가 끊김, 스캔 | PDFBox로 글자 좌표·괘선 추출 → 괘선으로 표 격자 재구성(`PdfLayout.java`, `pdf_model.py`). 스캔은 미지원(OCR 없음) |
| 공통 | 형식마다 결과 모양이 다름 | 하나의 DocumentModel + 원문 위치(Locator)로 통일 → 뒤 단계(평가 조립)는 형식을 몰라도 됨 |
