# HWP·HWPX 원본 대조 방식 설계 (2026-11-10)

## 1. 지금 PDF 검토가 하는 일

1. 관리자가 자기 PC의 원본 PDF를 고른다 → 2. 브라우저가 SHA-256을 계산해 서버 `checksum`과 비교 → 3. 일치하면 브라우저 PDF 보기로 연다 → 4. 근거 쪽을 보고 값을 확인 → 5. "대조했다" 체크 후 확정.

HWP·HWPX는 3번이 안 된다(브라우저가 HWP·HWPX를 정확히 표시하지 못함). 서버는 원본을 보관하지 않는다.

## 2. 대안 비교

| 기준 | A. 관리자 로컬 원본 + 외부 한글 프로그램 | B. 서버 원본 Storage + 열람 기능 | C. 검토용 PDF 변환본 |
|---|---|---|---|
| 원본 동일성 | 브라우저 SHA-256 대조(관리자 브라우저 계산값) | 서버가 직접 계산·보관 | 원본 SHA + 변환본 SHA 별도 보관 |
| 원문 보기 | 한글 프로그램(화면 밖) | 서버 뷰어(HWP 렌더러 필요) | 브라우저 PDF 보기 |
| 위치 연결 | 화면이 Locator(구역·표·행·열)를 보여주고 사람이 찾아감 | 뷰어가 Locator로 바로 이동 가능(구현 필요) | 변환 결과에 Locator 매핑 필요(변환기가 위치를 보존해야 함) |
| 화면이 확인할 수 있는 것 | 파일 동일성만. 어떤 칸을 봤는지는 확인 못함 | 열람 기록 | 변환본 열람 |
| 필요한 결정 | 수동 확인 기록 절차(이 문서), D-1, M-4 | File Storage(API-OD-A03), 접근 권한·보존 정책, 뷰어 기술 | 변환기 선택·검증, 변환 실패 처리, 변환본 보관 |
| 비용·복잡도 | 낮음 | 높음 | 중간~높음 |
| 위험 | 사람 확인을 시스템이 증명하지 못함 | 개인정보·저작물 보관 책임 | 변환본 쪽 번호를 원본 쪽처럼 오해(금지) |

## 3. 권장

- **단기(승인 시): A안을 "관리자 수동 확인 기록"으로 제한 도입.** 화면·API·보고서 어디에서도 "자동 원문 검증"이라고 부르지 않는다.
- **장기: B안**(Storage 결정 뒤). 서버가 원본을 가지면 Locator 위치의 실제 글을 꺼내 `extractedText`와 대조할 수 있어, 사람 확인을 돕는 자동 검사가 생긴다.
- **보조 후보 A′(HWPX만):** HWPX는 ZIP+XML이라 브라우저가 관리자 로컬 파일에서 Locator 칸의 글을 읽어 화면에 띄울 수 있다(파일 전송 없음). HWP 바이너리는 불가. Frontend 라이브러리(ZIP 해제) 도입 승인이 필요하다.
- C안은 변환기가 Locator와 페이지의 관계를 보존한다는 근거가 생길 때까지 보류. 변환 PDF의 쪽 번호를 원본 쪽이라고 표시하지 않는다.

## 4. A안 관리자 절차 (승인 후)

1. 관리 화면에서 Revision을 연다(형식 HWP·HWPX, 실험 배지).
2. 자기 PC의 원본 파일을 고른다 → 브라우저가 SHA-256 계산 → 서버 `checksum`과 일치해야 다음 단계.
3. 같은 파일을 **한글 프로그램**으로 연다(화면 밖).
4. 확인할 값마다 화면의 "분석기가 기록한 위치"(구역·표·행·열·경로·원문 인용)를 보고, 한글 프로그램에서 그 칸을 찾아 값이 맞는지 본다.
5. 값을 고치거나 그대로 두고, 근거 Locator(분석 Run에 있는 것 중 하나)를 고른다.
6. 학업 과목 ID를 입력한다(서버가 슬롯 과목 검증).
7. "한글 프로그램에서 위 위치의 원문을 직접 대조했습니다" 확인을 **관리자가 직접** 체크한다(자동 체크 없음).
8. 확정 → 서버는 `sourceCheck{method: LOCAL_FILE_EXTERNAL_VIEWER, localFileSha256}`, 필드별 근거 Locator, `analysisId`, 검토자를 저장한다.

## 5. 원문 확인 조건 (확정 허용 전제)

지시서의 10개 조건과 현재 상태(관리 화면 "확정 준비 상태" 점검표로 표시, 브라우저 확인 6/6):

| # | 조건 | 지금 |
|---|---|---|
| 1 | 검토 가능한 원본 확보 | 화면에서 확인(파일 선택) |
| 2 | 저장 SHA-256 = 원본 | 화면에서 확인(해시 대조) |
| 3 | 학업 과목 ID 매핑 | 화면 입력 + 서버 검증(현행) |
| 4 | 검토 대상 항목 확인 | 화면에서 선택 |
| 5 | 값의 문서 Locator 확인 | 화면 표시(분석기가 기록한 위치) |
| 6 | 관리자 원문 대조 | **승인 대기**(수동 확인 기록 절차) |
| 7 | 명시적 확인 행동 | **승인 대기**(체크 비활성) |
| 8 | 확정값 근거 Locator 저장 | **승인 대기**(D-1) |
| 9 | 검토 사용 `analysisId` 보존 | 현행 |
| 10 | 권한 검증 | 서버(현행) |

6~8이 풀리기 전에는 `review_not_supported`를 유지한다.

## 6. 보안·제약

- 원본은 브라우저 밖으로 나가지 않는다(해시만 계산). 서버에 원본·원문 전체를 보내지 않는다.
- `localFileSha256`은 관리자 브라우저가 보낸 값이라 조작된 클라이언트면 거짓일 수 있다 → "관리자 확인 기록"이지 증명이 아니다. 감사에는 검토자 ID·시각·방법을 함께 남긴다.
- SHA 일치·AI 분석 성공·Locator 구조 검증 중 어느 것도 확정 근거가 되지 않는다. 확정은 사람의 확인 행동이 있어야 한다.
- 합성 데이터로 한 검토 시험은 "합성 데이터 기반 검토 API 시험"으로만 기록한다.
- 관리자 인증은 아직 Mock이다. 실제 관리자 인증 전에는 확정자 신원을 운영 기록으로 쓸 수 없다.
