# 학생 케어 개선안 결과 (2026-11-07)

기존 학생 케어(`/student-care`)는 그대로 두고, 같은 API·판정·저장 기능을 쓰는 개선안을 `/student-care/ops`(메뉴 "학생 케어 개선안")로 만들었다. 기존 지표와 기능은 모두 남겼다. 예외는 두 가지다. 학습관별 칸의 분포 범위(중간 50%) 숫자는 사용자 지시(2026-11-07, 관리자에게 필요 없는 산출 기준 표기 제거)로 화면에서 뺐고, 학생 선 여러 개를 겹쳐 그리는 비교는 날짜 표 비교(최대 3명)로 바꿨다(`contract-changes.md`). 데이터는 로컬 DB 예시(강남 150 · 분당 50 · 수지 10명, 기준일 10/27)이며 실제 운영 데이터가 아니다.

## 1. 바뀐 화면

학생별 탭은 학생 한 명을 한 줄(24px)로 쓴다. 줄마다 사유 칩(예: `결석 4일 연속·미제출`, `학습 −9시간 45분 (−55%)`), 7일 출결·제출 띠, 같은 축의 학습 시간 막대와 "7일 / 평소 주" 시간, 진행률이 있다. 상담 필요 학생이 위로 오고 왼쪽에 주황 선이 있다. 명부 위 선택 상자로 사유별(결석, 학습 감소, 진행률, 입실 늦어짐, 과목 비중, 계획 미제출, 관리 중 등) 학생만 모아 볼 수 있다. 학생을 누르면 오른쪽에 고정된 상세가 바뀐다. 1279px 이하에서는 학생을 누르면 상세만 보이고 "← 명부로"로 그 학생 줄에 돌아온다. 상세는 날짜 열 7개를 공유하는 표(출결·계획·학습 실제/평소·입실 시각/평소/차이·진행률 실제/계획), 35일 출결 달력, 과목 비중, 상담 기록, 전체 관리 이력으로 이뤄진다.

학습관별 탭은 지표별 카드 4개를 날짜 열을 공유하는 표 하나로 합쳤다. 칸에는 결석/등원 예정, 학습 시간 평균과 평소 대비 변화(중앙값), 입실 시각 평소 대비 변화(중앙값), 계획 제출률이 있다. 칸을 누르면 그 날짜·지표의 학생 전원이 실제·평소·차이와 함께 아래 표에 나오고, 최대 3명을 골라 7일 값을 같은 날짜 열의 표에서 비교할 수 있다. 관리 이력 탭은 기존 컴포넌트를 그대로 쓴다.

`scripts/research/care-screen-metrics.mjs`로 기존(`baseline-v3/`)과 개선안(`ops-final3/`)을 같은 조건(3폭 × 2테마, 3개 지점)에서 쟀다. 표는 1600px 라이트, 강남 150명이다.

학생별 텍스트는 1차 구현에서 2,802자까지 줄였다가, Codex 기능 심사가 지적한 정확값(평소 주 시간, 시:분 단위, 같은 요일 평소, 실제/계획 분, 과목 비중 소수점)을 되살리면서 4,009자로 늘었다. 이후 사유 필터와 좁은 화면 상세 전환을 더했고, 관리자에게 필요 없는 산출 기준 문구("평소 = 이전 4주 같은 요일", "연속은 등원 예정일 기준", 분포 범위, 제외 기능 설명)를 빼서 3,952자가 됐다. 값을 다시 숨기지 않고 미달로 남겼다. 150행에 이름·반·사유·시간이 한 번씩 들어가는 최소량이 약 3,000자라 목표 2,800자는 행 수 대비 낮게 잡은 값이었다. 수지점(10명) 학생별 초기 텍스트는 상세가 자동으로 열려 있어 476자 → 825자로 늘었고 상세를 연 상태끼리 비교하면 980자 → 825자다.

학습관별 수치는 아무 칸도 열지 않은 상태다. 칸을 연 상태는 `scripts/research/care-open-state-metrics.mjs`로 따로 쟀다(`open-state-metrics.json`, 1600px). 결석 칸(10/22)을 열면 507자 · 1.5화면, 학습 시간 칸(10/22)을 열면 그날 입실한 학생 전원이 나와 3,204자 · 6.5화면(목록 안 스크롤 포함), 여기에 2명을 비교에 넣으면 3,416자 · 6.7화면이다. 지표 이름(7일 학습 감소)을 열면 해당 학생만 나와 830자 · 1.5화면이다. 전원 목록이 긴 것은 학생 개인 값을 모두 보여 달라는 1차 심사 V01을 따른 결과이며, 목록은 높이 360px 안에서만 스크롤된다. 390px도 같은 순서로 1.7 · 6.7 · 6.9 · 1.8화면이고 가로 넘침은 없다.

390px에서 학생별 명부는 12.4화면(기존 측정 없음)이다. 행이 세로 카드로 바뀌기 때문이며, 학생을 누르면 상세만 보이고(2.2화면) "← 명부로"가 그 학생 줄로 돌려보낸다.

## 3. 과업 시험

화면마다 새 Codex 시험관이 소스·API·정답 없이 화면 조작 기록기만으로 15문항(읽기 13, 쓰기 2)을 풀었다(`task-test.md`, 채점 `scripts/research/care-task-score.mjs`). 화면별 시험 전에 DB를 같은 초기 상태로 되돌렸다.

| | 기존 | 개선안 |
|---|---:|---:|
| 점수 (150점) | 125 | 150 |
| 읽기 문항 조작 수(클릭·입력·스크롤·자동 이동) | 450 | 41 |
| Q9 상담 저장 조작 수 | 27 | 17 |
| Q10 설정 변경·복원 조작 수 | 11 | 10 |

표는 최종 화면(문구 정리 후)으로 한 3차 시험이다. 기존에서 10점을 받은 12문항은 개선안에서도 모두 10점이고, 개선안은 기존이 놓친 Q3(기존 5점)·Q4(0점)·Q15(0점)까지 15문항 모두 10점이다. Q3·Q4는 "표시가 있는 학생"을 서버 사유로 읽어야 맞는 문항이다. 기존 화면 시험관은 날짜별 기준을 넘은 학생으로 읽었고, 개선안 3차 시험관은 사유 필터로 서버 사유 학생을 모아 맞혔다. 문항 문구는 두 화면 비교를 위해 바꾸지 않았다.

개선안 1차 시험은 130점, 2차는 135점이었다. 1차는 Q14(과목 비중 차이가 가장 큰 과목)를 틀렸다. 상세가 과목 비중을 정수로 반올림해 두 과목의 차이가 같아 보인 탓이었다. 소수 첫째 자리와 차이(%p)를 표시하도록 고친 뒤 새 시험관으로 다시 시험했다. 1·2차 기록은 `task-runs/ops-run1/`, `ops-run2/`에 남겼다. 3차 전에 채점기의 Q9(시험 전 이력에 없던 새 케이스만 인정)·Q10(첫 저장과 둘째 저장 사이의 수지점 설정 조회만 인정)을 더 엄격하게 고쳤고, 기존 화면 기록을 같은 채점기로 다시 매겨도 125점 그대로였다. 기존 화면 시험 뒤 채점기 버그 2건(Q9 이력 날짜 글, Q11 사유 이름 차이)을 고쳤고 두 화면에 같은 채점기를 썼다.

## 5. 검증

Admin 타입 검사·lint·build 통과, 개선안 모델 테스트 9건, 시드 생성기 테스트 6건, 조작 기록기 회귀 테스트 1건, E2E 타입 검사 통과. 기존 수용 E2E(`e2e/tests/student-care-*.spec.ts`)는 150명 기준으로 인원 값만 바꿔 두었으나 이번 환경에서 끝까지 실행하지 못했다(실행 중 세션이 끊김). 상담 저장과 설정 변경·복원은 두 화면 과업 시험(Q9·Q10)에서 서버 재조회로 확인했다.

## 6. 남은 것

학생별 텍스트(3,952자)는 계획 목표를 넘는다. 재확인 처리(관리 중 학생의 확인일 도래)는 데이터에 해당 학생이 없어 실행 검증하지 못했다. 시험관이 사람 운영자가 아니라 Codex라서 점수는 기존 화면과의 상대 비교로만 쓴다. 비전 AI 관찰은 응답 형태 초안(`vision-contract-draft.md`)까지만 썼고 화면에는 넣지 않았다. 계획에서 핵심 개선 이후 별도로 추가하기로 했고 서비스 백엔드와 촬영 주기가 정해지지 않았기 때문이다.
