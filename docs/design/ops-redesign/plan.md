# 학생 케어 운영자 개선 작업 계획서 (5판 기준 추가)

작성 2026-11-07. 1판은 Codex 계획 검사에서 65점(`reviews/00-plan-result.md`), 2판은 78점(`reviews/01-plan-result.md`), 3판은 83점(`reviews/02-plan-result.md`)으로 불통과했다. 0단계 3회 연속 불통과이므로 4장 규칙에 따라 0단계 산출물(시험 데이터·문항·기록기·측정기)을 다시 만들었다. 4판도 불통과하면 진행을 멈추고 보고한다. 지적마다 고친 위치를 마지막 두 절에 적었다. 반영이 충분한지는 다음 검사가 판단한다. 사용자는 작업 중 응답할 수 없으므로 단계별 승인은 Codex 검사가 대신한다.

## 0. 5판 재설계 기준 (2026-11-07 사용자 피드백)

4판 결과(`result-2026-11-07.md`, Codex 최종 채점 96점 통과)를 사용자가 직접 보고 목적을 잃었다고 판단했다. 아래 기준이 1–8장의 숫자 목표보다 앞선다. 숫자 목표는 이 기준을 지킨 안끼리 비교할 때만 쓴다.

| 번호 | 기준 | 4판에서 어긴 모습 |
|---|---|---|
| P1 | 학생별 탭은 학생 한 명씩 개별로 상세히 보는 곳이다. 목록은 학생을 고르는 수단이고, 상세는 화면 폭을 넉넉히 쓴다 | 명부 행마다 7일 띠·막대를 넣고 좁은 상세 패널을 옆에 붙여 목록도 상세도 아닌 중간이 됨 |
| P2 | 학습관별 탭은 학습관 전체 지표가 잘 보이는 곳이다 | 학생 목록·비교 표가 학습관 지표 아래로 계속 늘어남 |
| P3 | 페이지 스크롤과 겹치는 내부 스크롤(가로·세로)을 두지 않는다 | 상세 패널 세로 스크롤 + 7일 표 가로 스크롤로 스크롤바 2개 |
| P4 | 공간이 넉넉하면 우겨넣지 않는다. 글자·값이 숨 쉴 간격을 둔다 | 1600px에서도 상세 7일 표가 잘려 가로 스크롤 |
| P5 | 표현이 범례·단위 설명 없이 읽혀야 한다. 화면 위에 범례나 "위 줄 ○○ · 아래 줄 ○○", "(시간:분)" 같은 해독 문구가 필요하면 그 표현을 바꾼다. 범례가 필요한 표현은 지표가 늘 때(비전 관찰 등) 범례도 같이 늘어 확장되지 않는다 | 명부 위 범례 5개와 "위 줄 출결 · 아래 줄 계획 제출", 열 제목 "7일 / 평소 주 (시간:분)" |
| P6 | 비전 AI 관찰(`vision-contract-draft.md`)을 화면에 넣는다. 예시 데이터임을 표시하고, 판정에는 넣지 않으며, 사진 표본 비율을 시간·집중도로 바꾸지 않는다 | 6장 5단계를 실행하지 않고 끝냄 |
| P7 | 시안은 구조가 서로 다른 3개를 메뉴에 "학생 케어 A/B/C"로 붙인다. 명부 일부만 바꾼 변형은 시안으로 세지 않는다. 시안을 줄이거나 지우기 전에 사용자에게 보고한다 | URL 파라미터로 명부만 바꾼 3안을 만들고 임의로 2개 삭제 |

채점(Codex)은 P1–P7 위반을 필수 위반으로 본다. 텍스트 양·탐색 거리 같은 숫자는 P1–P7을 지킨 상태에서 기존 화면과 비교한다.

## 1. 목표

첫째, 운영자 입장의 기능 개선. 운영자가 화면을 보자마자 관리가 필요한 학생과 이유를 알고, 학생을 찾아 기록하고 다음 확인일을 정하는 일까지 더 쉽게 끝낼 수 있어야 한다. 도움말·튜토리얼은 보조이며 우선순위는 그 자체로 이해되는 디자인이다. PM 관점의 사용 가이드를 함께 만든다.

둘째, 기존 지표 표현 개선. 학생이 많을 때(강남점 150명) 한눈에 볼 수 있어야 하고, 한 학생의 지표를 가능하면 한 화면에서 볼 수 있어야 한다. 지표마다 지금 표현이 의미를 제대로 전하는지 다시 검토한다. 예를 들어 결석은 횟수보다 연속 여부나 날짜 패턴이 중요할 수 있다.

## 2. 지켜야 할 것

**기능과 지표를 줄이지 않는다.** 값이 화면 어딘가에 있는 것으로는 부족하고, 기존과 같은 동작이 되어야 한다. 구현 전에 `function-map.md`에 요구 ID별로 기존 위치, 새 위치, API 원천, 접근 경로, 검증 방법을 적고, 구현 후 항목마다 실행 검증 결과를 채운다. 대상은 다음 전부다.

| 영역 | 유지할 기능·정보 |
|---|---|
| 상단 | 지점 전환(강남 150 · 분당 50 · 수지 10), 기준일, 관리 기준 설정(8개 항목 조회·변경·저장), 학부모 리포트 미리보기 링크 |
| 학생별 | 이름·반 검색, 전원 명부(정상 학생 포함), 상태(상담 필요·관리 중·기록 부족 등)와 문제 학생 우선 배치, 학습 시간 7일 합계/기준 주평균, 입실 일수, 계획 제출 일수, 계획 대비 진행률 |
| 학생 상세 | 7일 출결·제출, 학습 시간과 요일 평균, 입실 시각과 요일 평균, 계획 대비 진행률, 과목별 계획·실제 비중, 상담 기록(기록자·방법·내용·결과·다음 확인일) 저장, 재확인 처리, 과거 관리 이력 |
| 학습관별 | 4개 지표(학습 시간·입실 시각·결석·계획 제출)의 학습관 전체 상태, 개인 평소 대비 변화, 변화가 큰 학생 식별과 상세 이동, 학생 제외·복원 |
| 관리 이력 | 학생 필터, 날짜순 기록, 기록 원문 펼침, 이력 없음 상태(G54) |
| 판정 | 초기값에 따른 문제 학생 식별, 운영자 설정 변경 반영. 백엔드 판정 공식은 바꾸지 않는다 |
| 상태 | 로딩·빈 상태·오류(503 등)·재시도 구분, 지점 전환 후 오래된 목록 복구 |

**필수 통과 조건은 점수로 상쇄하지 않는다.** 다음 중 하나라도 어기면 그 단계는 총점과 관계없이 불통과다: 유지 목록 기능 누락, 데이터 의미 왜곡(결석·미확인·0 혼동 등), 정상 학생 숨김, 필수 사유를 툴팁이나 숨은 영역으로만 제공, 접근성 속성 제거로 수치를 낮춤, 기준점보다 작은 글씨나 잘린 글씨, 1600/850/390px·라이트/다크 중 하나에서 가로 넘침·겹침, 콘솔 오류.

**계약 충돌은 기록한다.** `student-care-feedback-contract.md`(F01–F24)와 `student-care-feedback-gate-2026-10-28.md`(G01–G54)와 충돌하면 이번 목표를 우선하되, `contract-changes.md`에 항목 번호, 바꾼 이유, 근거 측정값을 적는다. 사용자가 바꾼 지점 인원(G07: 60/30/10 → 150/50/10)도 기록한다.

**원본 화면을 보존한다.** 기존 `/student-care`는 그대로 두고 개선안은 새 경로 `/student-care/ops`, 메뉴 "학생 케어 개선안"으로 만든다. 백엔드 판정 공식, DB 스키마, API 응답 형태는 바꾸지 않는다.

**불통과 처리.** 한 단계에서 Codex 검사를 통과하지 못하면 지적을 고쳐 다시 받는다. 3회 연속 불통과면 한 단계 앞으로 돌아가 그 단계 산출물부터 다시 만든다. 그래도 통과하지 못하면 진행을 멈추고, 통과하지 못한 항목·원인·현재 상태를 최종 보고에 적는다. 불통과 상태로 다음 단계에 가지 않는다.

**검증 명령.** 단계 3·4에서 매번 실행한다. 실행 조건: admin FE 5174(`frontend/admin/.env.local`의 `VITE_CARE_API_TARGET=http://127.0.0.1:8081`), care 백엔드 8081(프로필 `care-demo,e2e`, `app.fixed-date=2026-10-28`, `learnershigh.mock.database-examples=true`), MySQL 3337, 브라우저는 설치된 Chrome에 `--no-proxy-server`. 명령: `npm --prefix frontend/admin run typecheck`, `npm --prefix frontend/admin run lint`, `npm --prefix frontend/admin run build`, 학생 케어 모델·API Node 테스트(`node --test frontend/admin/src/features/student-care/**/*.test.mjs` 해당 파일), `node --test scripts/research/care-task-harness.test.mjs`, `node --test scripts/demo/generate-care-seed.test.mjs`, 측정기 `node scripts/research/care-screen-metrics.mjs student-care/ops <out> 1600,850,390 light,dark`와 원본 회귀 확인용 `... student-care <out> ...`(원본 수치가 `baseline-v3`와 같아야 함). 기존 Playwright spec(`e2e/tests/student-care-*.spec.ts`)은 13명 고정 데이터 프로필을 전제로 해 이 DB에서 돌리면 인원 단정이 맞지 않는다. 그래서 E2E는 `npm --prefix e2e run typecheck`(타입 검사)만 하고, 실행 실패가 앱 결함인지 환경 차이인지 섞이지 않게 원본 회귀는 측정기 수치 비교로 대신한다. 측정기는 지점 인원(150/50/10명)이 화면에 없거나 첫 문제 학생 상세를 열지 못하면 즉시 실패한다.

## 5. 개선 판정

**과업 시험.** 문항·실행 절차·채점은 `task-test.md`에 고정했다(최종 4판: 15문항 150점, 변경 이력은 그 문서 끝). 요약하면, 15문항(읽기 13, 쓰기 2)을 화면마다 새 Codex 시험관이 조작 기록기만으로 풀고, 화면별 시험 전에 DB를 같은 초기 상태로 복원한다. 쓰기 문항은 저장 요청 내용·횟수와 서버 재조회로 채점하므로 아무것도 하지 않고는 점수를 받을 수 없다. 개선안은 총점이 기존보다 높고, 기존에 맞힌 문항을 틀리지 않으며, 쓰기 문항의 조작 수가 기존 이하여야 한다. 재확인 처리와 학생 제외·복원은 과업 대신 `function-map.md`의 실행 검증으로 확인한다(이유는 `task-test.md`).

**상세까지 포함한 측정.** 측정기는 학생별 탭에서 첫 문제 학생의 상세를 열어 같은 지표를 따로 잰다. 선택 후에만 그리는 방식으로 초기 수치를 줄이는 우회를 막기 위해서다. 페이지 분할이나 가로 탐색으로 부담을 옮기는지는 과업 시험의 조작 로그(자동 이동 포함)로 확인한다.

## 6. 비전 AI 지표

비전 표시는 기존 지표 개선과 분리한다. 4단계까지 통과한 뒤 5단계에서 추가하고, 추가 후 4단계 측정을 다시 돌려 핵심 결과가 나빠지지 않는지만 확인한다. 비전으로 핵심 개선 점수를 얻지 않는다. 서비스 백엔드가 없으므로 프론트엔드 예시 데이터로 보여주고 "예시"를 표시한다. 관찰 4개(`person_visible`, `head_down`, `phone_interaction`, `reading_or_writing`)는 항목별 yes·no·unknown 장수를 보존하고, 겹칠 수 있는 관찰을 누적 막대로 쌓지 않으며, 사진 비율을 시간·집중도로 바꾸지 않는다. 판정 공식에는 넣지 않는다. 응답 형태 초안은 `vision-contract-draft.md`에 쓰고 공유 문서 `api-contract.md`는 바꾸지 않는다.

## 7. 디자인 기준과 참고자료

새 디자인 시스템을 따로 만들지 않는다. 기존 토큰(`index.css`, `app/theme.css`)을 `design-tokens.md`로 정리하고 개선안은 그 토큰을 쓴다. 바꾸는 값은 근거와 함께 개선안 범위에서만 바꾼다.

참고자료는 1단계에서 실제로 읽고, 출처마다 "인용한 원칙 → 적용 또는 불적용 → 이 화면에서의 한계"를 쓴다. 기존 선택을 지지하는 근거도 남긴다(바꾸기 위한 변경 금지). 1단계 문서는 별도 에이전트가 먼저 초안을 쓰고, Codex 근거 검사를 통과해야 확정한다. 후보는 Stephen Few의 대시보드 설계, Tufte의 스파크라인과 작은 다중 차트, Cleveland & McGill의 시각 인지 정확도, NN/g의 데이터 표 글, ONS·GOV.UK 시각화 지침이며, 기존 조사 문서의 출처(Datadog, FPP3, Grafana, NIST 등)는 재사용한다. 사용할 스킬은 `dataviz`(차트 형식·색 검증)이며, 1단계 문서에 스킬에서 가져온 규칙과 적용 결과를 적는다.

## 8. 데이터와 실행 조건

비교 데이터를 고정한다. `data-snapshot/`에 지점, board, metrics, 설정(3개 지점), 과업 학생 8명의 상세·이력, 커밋 해시, 시드 파일 해시, 작업 트리 변경 목록을 저장했다. 기준일은 10/27, 업무일은 백엔드 `app.fixed-date=2026-10-28`로 고정했고 상담 폼은 상세 응답의 `today`를 다음 확인일 계산에 쓴다(기존 `RosterStudies.tsx`). 시드는 3판 심사 후 결석 패턴 비교를 위해 흩어진 결석 4명·매주 목요일 결석 4명을 더했고(정상 저녁형 33 → 25명), 강남 상담 필요는 49명, 관리 중은 5명이다. 상담·설정 테이블의 초기 상태는 `scripts/research/care-db-state.sh save initial`로 덤프했고(`db-state/initial.sql`), 화면별 시험 전과 쓰기 검증 뒤에 `restore initial`로 되돌린다. 복원 후 board가 상담 필요 49명·관리 중 5명인 것을 확인했다.

학생 61~100번은 이번 확대로 지점이 바뀌어 기존 상담 예시 일부가 다른 지점 학생에게 붙어 보일 수 있다. 이 학생들의 기존 이력은 평가에서 빼되, 이력 기능은 지점이 바뀌지 않은 학생(1~60번, 예: 관리 중 `demo_s014`, `demo_s035`)의 기존 기록과 시험 중 새로 만든 기록으로 검증한다.

**반례 검증.** 기존 반례 13개(`student-care-metric-cases-2026-10-28.json`)는 1단계 문서에서 반례마다 선택한 표현, 기대 화면, 검사 단계를 연결한다. 시드 데이터에 있는 반례(정상 개인 차이 4종, 지속 감소·지연, 일시 변화, 실행 차이, 과목 변화, 미제출, 결석, 회복, 기록 누락)는 실제 화면에서 확인한다. 시드에 없는 반례(집단 전체가 함께 변해 분포 밖 학생이 0명인 경우, 하루 극단값이 반복 감소를 상쇄하는 경우)는 개선안의 집계 모델 함수에 합성 입력을 넣는 Node 테스트와, 같은 입력을 화면에 그린 캡처로 확인한다. 시드 데이터를 이 반례에 맞춰 고치지 않는다. 폭·테마 검사는 1600/850/390px × 라이트/다크를 매 단계 3·4에서 돌린다.

## 9. 위험

과업 시험의 시험관이 사람 운영자가 아니라 Codex다. 결과는 기존 화면과의 상대 비교로만 쓰고 사용성 증명으로 쓰지 않는다. 150명 데이터는 기존 100명 시나리오 비율을 2.1배로 늘린 합성 데이터라 실제 분포와 다를 수 있다. 작업은 로컬 브랜치 `feat/student-care-ops-redesign`에 단계별로 커밋하고 push하지 않는다.
