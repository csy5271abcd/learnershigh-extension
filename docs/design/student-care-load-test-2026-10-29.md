# 학생 케어 조회 API 부하 테스트 (2026-10-29)

## 요약

학생 수가 늘면 학생별 목록(`/board`)과 학습관 지표(`/metrics`)가 학생마다 원본 학습 기록을 따로 조회했다. 학생 1000명이면 요청 한 번에 SQL이 1,005개 나갔다. 일괄 조회로 바꾸고 응답 압축을 켰으며, 쌓인 상담을 훑던 조회에 인덱스를 추가했다. 동시 접속(k6)과 데이터 누적(학생 10,400명, 상담 이력 8만 건) 조건도 확인했다.

| 학생 1000명 기준 | 개선 전 | 개선 후 |
| --- | --- | --- |
| 요청당 SQL 수 (`/board`) | 1,005 | 7 |
| `/board` 응답 시간 p50 | 853ms | 224ms |
| `/metrics` 응답 시간 p50 | 839ms | 239ms |
| `/board` 동시 10요청 처리량 | 6.6 rps | 11.0 rps |
| `/metrics` 전송 크기 | 3,136KB | 57KB (gzip) |

## 환경과 방법

- 장비: 로컬 PC 1대(AMD Ryzen 5 9600X, 메모리 31GB). 서버 JVM `-Xmx1g`, Java 25, MySQL 8.4(Docker).
- 서버·DB: 시연용과 분리한 DB(`student_care_load`)와 서버(8083 포트)에서 측정했다. 기준일은 2026-10-28로 고정했다.
- 데이터: 기존 합성 학생 100명의 시나리오(정상, 학습 감소, 입실 지연, 기록 누락 등)를 복제해 100·300·1000명 학습관을 만들었다. 학생마다 35일 기록이 있다.
- 측정: 엔드포인트마다 예열 3회 후 20회 요청. 동시 요청 수 1·5·10. SQL 수는 MySQL `Com_select` 증가분으로 셌다.
- 한계: 같은 PC에서 클라이언트·서버·DB가 함께 돌았다. 네트워크 지연과 실제 LearnersHigh 원본 API 응답 시간은 포함되지 않았다. 각 조건 1회 측정이다.

## 원인

`StudentCareQueryService`의 `board`와 `metrics`가 학생 목록을 돌면서 `findDailyStudy(studentId)`를 학생마다 호출했다. SQL 수가 학생 수 + 상수로 늘었고 응답 시간도 학생 수에 비례했다.

## 개선

1. **일괄 조회**: `ExistingStudyClient.findDailyStudies(studentIds, from, to)`를 추가했다. 로컬 예시 원본은 `IN` 조건으로 500명씩 묶어 한 번에 읽는다. 기본 구현은 학생별 조회를 반복하므로 다른 구현체는 그대로 동작한다. 실제 LearnersHigh 연동에서는 출결·계획 제출을 지점 단위 API(`select_study_reports_period`) 한 번으로 읽을 수 있다. 다만 과목별 계획·순공 API는 원본이 학생 단위라 학생 수만큼 호출이 남는다(`docs/architecture/existing-learnershigh-data.md` §5-3).
2. **응답 압축**: `server.compression`을 켰다(JSON, 2KB 이상). 1000명 `/metrics`는 3,136KB → 57KB, `/board`는 167KB → 4KB다. 압축 비용으로 1000명 기준 서버 처리 시간이 10~20ms 늘었다. 로컬 측정에서는 전송 시간이 거의 없어 이득이 보이지 않지만 10Mbps 회선이면 3MB 전송에만 약 2.5초가 걸리므로 실제 환경에서는 압축 쪽이 크게 유리하다.

3. **쿨다운 조회 인덱스**: 관리 종료 후 다시 표시하지 않을 학생을 찾는 조회(`branch_id`, `status = CLOSED`, `closed_on` 범위)가 지점의 상담 전체를 훑었다. 인덱스를 `(branch_id, status, closed_on)`으로 넓혔다(`V202610290800`). 1000명 지점·상담 2,000건 기준 5.3ms → 0.1ms. 상담이 해마다 쌓일수록 차이가 커진다.
4. **회귀 테스트**: 학생 10명과 100명 지점에서 `/board`·`/metrics`가 원본을 일괄 조회 1회로만 읽는지 검사한다(`WeeklyCareApiTest`). 학생별 조회가 다시 생기면 CI에서 실패한다.

동작은 바꾸지 않았다. Backend 단위 273건, MySQL 통합 104건이 통과했다.

## 데이터가 쌓였을 때 (DB 규모 확대)

부하 DB를 학생 10,400명(지점 12곳), 학습 기록 364,000행, 상담 20,800건, 상담 이력 83,200건으로 키웠다. 학생마다 1년치 상담 2건과 이력 8건이 쌓인 상태다. 주요 조회의 실행 계획(`EXPLAIN`)은 다음과 같다.

| 조회 | 사용 인덱스 | 읽는 행 |
| --- | --- | --- |
| 학생 500명 × 35일 학습 기록 | `demo_care_day` PK | 17,500 (필요한 만큼만) |
| 지점 학생 목록 | `demo_care_student.branch_id` | 1,000 |
| 관리 중 상담 | `idx_care_case_branch_status_closed` | 관리 중인 건만 |
| 쿨다운(최근 종료 상담) | `idx_care_case_branch_status_closed` | 39 (개선 전 2,000) |
| 학생 한 명의 이력 | `idx_care_event_student` | 8 |

## 동시 접속 (k6)

k6 v1.3.0(Docker)으로 학생 1000명 지점의 학생별 탭을 여는 요청(`/board` 2회 + `/metrics` 1회, 화면이 실제로 부르는 그대로)을 반복했다. 대기 시간 없이 계속 여는 최악 조건이다. 동시 접속자별로 40초씩 측정했다.

| 동시 접속 관리자 | 탭 열기 p50 | p95 | 초당 탭 열기 | 실패 |
| --- | --- | --- | --- | --- |
| 1 | 320ms | 391ms | 3.2 | 0% |
| 5 | 1.1초 | 1.4초 | 4.7 | 0% |
| 20 | 4.5초 | 5.3초 | 4.4 | 0% |
| 50 | 10.7초 | 11.3초 | 4.5 | 0% |

이 PC에서는 초당 약 4.5회가 처리 한계다. 그 이상은 대기열이 생겨 응답 시간이 접속자 수에 비례해 늘었고, 오류는 없었다. 관리자 한 명이 10초에 한 번 탭을 연다고 보면 1000명 지점에서 동시에 약 45명까지 대기 없이 처리한다. 이 한계는 계산·직렬화 CPU에서 온다. 아래 `/board` 중복 호출을 없애면 탭 한 번의 작업량이 약 1/3 줄어든다.

## 관리 이력 탭과 페이지네이션

관리 이력 탭(전체 학생)은 학생 목록을 받은 뒤 학생마다 이력 API를 따로 부른다. 이력 API에는 페이지 나누기가 없다.

| 지점 | 탭 한 번의 요청 수 | 로컬 소요 시간 |
| --- | --- | --- |
| 100명 | 101 | 0.3초 |
| 1000명 | 1,001 | 1.5초 |

로컬은 왕복 지연이 거의 없어 1.5초에 그쳤다. 실제 네트워크(왕복 30ms, 브라우저 동시 연결 6개)라면 요청 대기만 약 5초가 더해진다. 학생 한 명의 이력은 몇 년이 쌓여도 수십 건이라 학생별 조회는 문제가 없다. 지점 전체를 한 화면에 모으는 방식이 문제다. 해결책은 지점 단위 이력 API를 새로 두고 최신순 커서 페이지네이션(예: 50건씩, `created_at` + `record_no` 기준)으로 받는 것이다. API 계약 변경이 필요해 이번 범위에서는 제안으로 남긴다.

## 남은 개선 후보

- 관리 이력 탭: 지점 단위 이력 API + 커서 페이지네이션 (위 절).
- 학생 케어 5 화면은 처음 열 때 `/board`를 두 번 부른다(페이지 상단과 학생 목록). 한 번으로 줄이면 1000명 기준 서버 계산 약 220ms를 아낀다.
- 학생 목록·학습관 지표는 학생 전원을 한 번에 내려준다. 1000명 지점에서도 압축 후 57KB라 지금은 페이지를 나누지 않는다. 학습관이 수천 명 단위가 되면 목록 페이지네이션을 검토한다.
- 비교용으로 남겨 둔 이전 시안 화면 일부는 학생마다 상세 API를 따로 호출한다. 시연용 화면이라 대상에서 뺐다.

## 재현

```bash
node scripts/perf/generate-load-seed.mjs        # 100·300·1000명 지점
node scripts/perf/generate-volume-seed.mjs      # 추가 지점 9곳 + 1년치 상담 이력
node scripts/perf/run-load.mjs <label> http://127.0.0.1:8083
docker run --rm -v "$PWD/scripts/perf:/work" -w /work grafana/k6:1.3.0 run \
  -e BASE=http://host.docker.internal:8083 -e SCENARIO=roster -e VUS=20 k6-student-care.js
```

시드는 Flyway가 빈 DB를 초기화한 뒤 넣는다. k6 컨테이너가 접속하려면 측정용 서버를 `--server.address=0.0.0.0`으로 띄운다. 결과는 `scripts/perf/results/`에 저장된다(커밋하지 않음). k6는 CI에 넣지 않는다. 공용 러너는 성능 편차가 커서 시간 기준이 흔들리므로, CI에서는 위 쿼리 수 회귀 테스트로 대신한다.
